# Signaling Server Architecture

The signaling server is implemented in server/ws-server.js and is attached to the HTTP server created in server/server.js. It uses the ws package and keeps peer and room state in memory.

## Connection lifecycle

1. A client opens a WebSocket connection to /server.
2. The server validates a browser Origin against WS_ALLOWED_ORIGINS or, when no allowlist is configured, against the request Host.
3. Native clients may omit Origin. Origin validation protects browser contexts against cross-site WebSocket hijacking; it is not authentication.
4. The server creates a Peer object, sends ws-config and display-name metadata, and handles peer messages.

The WebSocket server sets maxPayload to 8 MiB per frame.

## Room types

- IP rooms: used for automatic discovery based on the peer IP value derived by server/peer.js.
- Secret rooms: used for persistent pairing. The secret is a bearer capability and is not a user account or database identity.
- Public rooms: use a short public room identifier and allow temporary peer discovery.

The server uses a null-prototype object for room maps so special property names such as __proto__ are not treated as inherited object properties.

## Authorization before relaying

Before relaying a message, the server checks that the sender is a member of the selected room and that the recipient is also present in that room. For IP-room chat messages, the server canonicalizes the room identifiers from the sender's authorized IP-room membership before forwarding.

## Pairing

The browser generates a six-digit pairing code and the server associates it with a high-entropy room secret. The code is temporary; the room secret is the long-lived capability persisted by the browser.

The server applies a per-peer request counter to pairing and selected room operations. This is not a global IP-based limit: a newly opened WebSocket creates a new Peer and a fresh counter. The HTTP Express rate limiter does not cover WebSocket upgrades.

## WebSocket fallback

When WS_FALLBACK is enabled, the server relays file chunks and messages. The server therefore handles the fallback payload. WebRTC DataChannel transfers are encrypted between peers; WebSocket fallback must not be described as end-to-end encrypted against the server.

## Operational security

- Keep HTTPS/WSS enabled.
- Configure a trusted reverse proxy to overwrite forwarding headers before they reach the application.
- Restrict direct access to the origin where possible.
- Keep DEBUG_MODE disabled in production.
- Enable and correctly configure RATE_LIMIT for HTTP traffic.
- Use short-lived TURN credentials and provider-side quotas.
