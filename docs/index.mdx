# ErikrafT Drop™ Documentation

Welcome to the official documentation for ErikrafT Drop™, a cross-platform peer-to-peer file and text transfer application. This documentation distinguishes the normal WebRTC path from optional server-relayed fallback behavior.

## Key Features

### WebRTC peer-to-peer transfers

The normal transfer path uses WebRTC DataChannels. WebRTC encrypts DataChannel traffic with DTLS. A TURN server may relay encrypted packets when a direct route is unavailable.

### Device pairing

Pairing uses a temporary six-digit code to exchange a high-entropy room secret. The secret is a bearer capability, not an encrypted database record. See [Device Pairing](features/device-pairing).

### WebSocket fallback

When enabled, file chunks and messages can be relayed through the Drop server. The fallback is enabled by default unless WS_FALLBACK=false. Because the server handles relayed payloads, do not describe this mode as end-to-end encrypted against the server. See [Configuration](reference/configuration).

## Security and Privacy

ErikrafT Drop™ does not require accounts and the repository does not implement a central file-storage database. The server still processes connection metadata such as IP address, user agent, display name, peer identifiers and temporary room identifiers.

- WebRTC DataChannel traffic is encrypted between peers.
- TURN relays encrypted WebRTC packets but sees connection metadata and traffic volume.
- WebSocket fallback relays payloads through the server and does not provide the same end-to-end confidentiality guarantee as WebRTC.
- The signaling server validates browser Origin values, but Origin is not user authentication. Native clients may omit it.
- Review the [Security Policy](https://github.com/erikraft/Drop/blob/master/SECURITY.md) before reporting a vulnerability.

## Performance

Transfer speed depends on the peers, network path, Wi-Fi/Ethernet, browser, device and whether TURN or WebSocket fallback is used. No fixed throughput figure is guaranteed.
