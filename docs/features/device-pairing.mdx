# Device Pairing

Device pairing lets two clients discover each other across different networks without creating user accounts.

## How pairing works

1. The initiating client requests a pairing session.
2. The server creates a temporary six-digit code and associates it with a high-entropy room secret.
3. The intended second client enters the six-digit code.
4. The server validates the code and adds both peers to the same secret room.
5. The clients persist the room secret in origin-scoped IndexedDB so they can discover each other in later sessions.

The six-digit code is a temporary rendezvous code. The room secret is the persistent bearer capability. Anyone who obtains a valid room secret may be able to join that secret room, so protect the browser profile and do not publish pairing data.

## Security properties and limits

- Pairing does not create an account or authenticate a real-world identity.
- The room secret is a random capability, not an encrypted record in a database.
- The server keeps current room membership and active pairing codes in process memory.
- The server checks room membership before relaying signaling and fallback messages.
- Pairing attempts are rate-limited per WebSocket peer. This is not a global IP-based brute-force control because a new WebSocket connection creates a new peer.
- Browser Origin validation is a CSWSH defense, not an authentication mechanism.

## Managing paired devices

Use the application's device management controls to remove a paired device. Removing the saved room secret from a browser profile stops that profile from automatically rejoining the secret room.

If you suspect that a pairing secret was exposed, unpair and establish a new pairing session so that the old capability is no longer used.
